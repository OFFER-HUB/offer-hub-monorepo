<Callout type="warning">
  OFFER-HUB does **not** provide an outbound webhook subscription API. There is **no** `POST /api/v1/webhooks` endpoint to register a URL, an event list, or a signing secret. The only real-time mechanism for integrators is the **SSE event stream** (`GET /api/v1/events`). The two `/webhooks` endpoints that exist are **inbound** receivers used by external providers (AirTM, Trustless Work) to notify your Orchestrator — you never call them as an integrator.
</Callout>

## Real-Time Events via SSE

The event stream is the supported way to receive real-time notifications about users, orders, escrows, balances, disputes, top-ups, and withdrawals.

<Badge variant="success">GET</Badge> `/api/v1/events`

### Authentication

The endpoint requires a valid API key:

- **Header:** `Authorization: Bearer ohk_live_...`
- **Scope:** the API key needs the `events.read` scope (a master scope `*` key also works)

### Connection Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `types` | `string[]` | Comma-separated event types to filter (e.g. `order.created,order.escrow_funded`) |
| `resources` | `string[]` | Comma-separated aggregate types to filter (e.g. `Order,Escrow,Balance`) |
| `since` | `string` | ISO timestamp cursor to replay events after (alternative to `Last-Event-ID`) |

Events are scoped to the marketplace tied to your API key, so each marketplace only receives its own events.

### Reconnection & Replay

The service keeps the last **1000 events for 1 hour** in Redis. If your connection drops, reconnect and pass the standard `Last-Event-ID` header (the `id` of the last event you received) to replay everything you missed:

```bash
curl -N http://localhost:4000/api/v1/events \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Last-Event-ID: 2026-02-02T20:43:52.832Z"
```

A heartbeat (`ping`) message is sent every **30 seconds** to keep the connection alive.

### Event Format

Events use the standard SSE format. The `data` field is the full JSON domain event:

```text
id: 2026-02-02T20:43:52.832Z
event: user.created
data: {
  "eventId": "evt_n_8yumeOFwqPnSbhvemqJ",
  "occurredAt": "2026-02-02T20:43:52.832Z",
  "eventType": "user.created",
  "aggregateId": "usr_jF5tBLUBhuSqdkU4Ryct8B1Oj4va4RiV",
  "aggregateType": "User",
  "payload": {
    "userId": "usr_jF5tBLUBhuSqdkU4Ryct8B1Oj4va4RiV",
    "externalUserId": "test-viva-05",
    "email": "viva5@test.com",
    "status": "ACTIVE"
  },
  "metadata": {
    "userId": "usr_jF5tBLUBhuSqdkU4Ryct8B1Oj4va4RiV"
  }
}
```

| Field | Description |
|-------|-------------|
| `eventId` | Unique event ID (`evt_...`) |
| `occurredAt` | ISO 8601 timestamp |
| `eventType` | Event type, e.g. `order.escrow_funded` |
| `aggregateId` | Resource ID the event belongs to (`ord_...`, `usr_...`, etc.) |
| `aggregateType` | Resource type (`Order`, `User`, `Balance`, …) |
| `payload` | Event-specific data |
| `metadata` | Correlation/user context |

### Examples

Listen to all events:

```bash
curl -N http://localhost:4000/api/v1/events \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

Listen only to order events:

```bash
curl -N "http://localhost:4000/api/v1/events?types=order.created,order.escrow_funded,order.released" \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

Listen only to escrow-related aggregates:

```bash
curl -N "http://localhost:4000/api/v1/events?resources=Escrow" \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

### Using the SDK

```typescript
import { OfferHubSDK } from '@offerhub/sdk';

const sdk = new OfferHubSDK({
  apiUrl: 'http://localhost:4000',
  apiKey: 'ohk_live_your_api_key'
});

const events = sdk.events.subscribe();

events.on('order.escrow_funded', (data) => {
  console.log('Escrow funded:', data);
});

events.on('withdrawal.completed', (data) => {
  console.log('Withdrawal completed:', data);
});
```

### Using EventSource (browser)

```typescript
const events = new EventSource(
  'http://localhost:4000/api/v1/events',
  { headers: { Authorization: 'Bearer ohk_live_...' } }
);

events.onmessage = (e) => {
  const event = JSON.parse(e.data);
  console.log(event.eventType, event.payload);
};
```

## Event Catalog

These are the event types you can subscribe to. Wildcard subscriptions are supported: `order.*`, `topup.*`, `withdrawal.*`, and `*`.

### User Events

| Event | Payload |
|-------|---------|
| `user.created` | `{ userId, externalUserId, type, status }` |
| `user.airtm_linked` | `{ userId, airtmUserId, linkedAt }` |
| `user.stellar_linked` | `{ userId, stellarAddress, linkedAt }` |

### Wallet Events

| Event | Payload |
|-------|---------|
| `wallet.created` | `{ userId, publicKey, provider, funded, trustlineReady }` |

### Balance Events

| Event | Payload |
|-------|---------|
| `balance.credited` | `{ userId, amount, source, newBalance, transactionHash? }` |
| `balance.debited` | `{ userId, amount, destination, newBalance }` |
| `balance.reserved` | `{ userId, amount, orderId, reservedBalance }` |
| `balance.released` | `{ userId, amount, orderId, reason }` |

### Top-Up Events

| Event | Payload |
|-------|---------|

## Inbound Provider Webhooks (Self-Hosting)

The Orchestrator exposes **two inbound webhook receivers** that external providers call to notify it about events. These are endpoints **your Orchestrator receives** — integrators never register or call them.

<Callout type="note">
  Because of the global `/api/v1` prefix, the full paths are `POST /api/v1/webhooks/airtm` and `POST /api/v1/webhooks/trustless-work`. Signature verification and deduplication are handled internally by the Orchestrator — no outbound configuration is needed.
</Callout>

### AirTM — `POST /api/v1/webhooks/airtm`

Receives pay-in/pay-out events from AirTM. The Orchestrator verifies the request using the standard Svix headers (`svix-id`, `svix-timestamp`, `svix-signature`) and the `AIRTM_WEBHOOK_SECRET` environment variable, then processes the event (deduplicating repeats).

### Trustless Work — `POST /api/v1/webhooks/trustless-work`

Receives escrow lifecycle events from Trustless Work. The Orchestrator verifies the HMAC-SHA256 signature in the `x-tw-signature` header using the `TRUSTLESS_WEBHOOK_SECRET` environment variable, then updates the escrow and emits the corresponding domain events on the SSE stream.

Both endpoints respond with `{ "status": "ok" }` and are covered by the `AIRTM_WEBHOOK_SECRET` / `TRUSTLESS_WEBHOOK_SECRET` environment variables documented in the [Configuration guide](/docs/configuration).
