Three endpoints need no credential and exist for clients, load balancers and monitoring. `GET /config` lives in `ConfigController` (`apps/api/src/modules/config/config.controller.ts`). The two health routes live in `HealthController` (`apps/api/src/modules/health/health.controller.ts`) and `HealthService` (`health.service.ts`). With the global `/api/v1` prefix from `apps/api/src/main.ts`, the paths below are the full routes.

| Method | Path | Scope | Success status | Controller handler |
| --- | --- | --- | --- | --- |
| <Badge variant="success">GET</Badge> | `/api/v1/config` | none (public) | `200 OK` | `ConfigController.getConfig` |
| <Badge variant="success">GET</Badge> | `/api/v1/health` | none (public) | `200 OK` | `HealthController.getHealth` |
| <Badge variant="success">GET</Badge> | `/api/v1/health/detailed` | none (public) | `200 OK` | `HealthController.getDetailedHealth` |

<Callout type="note">
  The TypeScript SDK (`packages/sdk`) has no resource for these routes, so the TypeScript examples use plain `fetch`. All three handlers are marked `@Public()`, which makes `ApiKeyGuard` skip them, so no `Authorization` header is needed.
</Callout>

## Common behavior

- **No scope and no request body.** None of these routes reads a body or declares `@Scopes`.
- **No idempotency.** All three are `GET` routes; the global idempotency guard only acts on `POST`, `PUT` and `PATCH`.
- **Rate limiting still applies.** The global `RateLimitGuard` allows 100 requests per 60 seconds, counted per IP for requests without a key. Poll health sparingly; a load balancer probe every 10 seconds is well within the limit.
- **Envelope differs per route.** `ResponseInterceptor` leaves a single-key `{ data: ... }` payload untouched and wraps everything else in `{ data, meta }`. So `GET /config` returns `{ "data": { ... } }` with **no `meta`**, while both health routes are wrapped as `{ "data": { ... }, "meta": { "requestId", "timestamp" } }`.
- **Errors** use `{ "error": { "code", "message" } }`. The only error these routes can realistically return is `429 RATE_LIMITED`; see [Error Codes](/docs/api-reference/errors).

## GET /api/v1/config

Returns platform configuration for clients that want to show limits or check which features are on.

<Callout type="warning">
  **The limits, currencies and provider names are hardcoded in the controller.** They are string literals in `getConfig`, not read from the environment, the database or the services that enforce rules. Changing a limit elsewhere will not change this response, and this response is not proof of what another endpoint accepts. Treat it as documentation of intent, and confirm real limits on the endpoint you call.
</Callout>

What is fixed and what is computed:

| Field | How it is produced |
| --- | --- |
| `currencies` | Fixed: `["USD"]` |
| `limits.topup` | Fixed: min `1.00`, max `10000.00` |
| `limits.withdrawal` | Fixed: min `10.00`, max `5000.00` |
| `limits.order` | Fixed: min `1.00`, max `50000.00` |
| `features.milestones`, `features.disputes` | Fixed: `true` |
| `features.sse` | Fixed: `false`, with a code comment "Not yet implemented", even though `GET /events` exists. Do not use this flag to decide whether to open the [event stream](/docs/api-reference/events) |
| `features.airtm` | Computed: `true` when the `AIRTM_API_KEY` environment variable is set |
| `features.trustlessWork` | Computed: `true` when `TRUSTLESS_API_KEY` is set |
| `providers.fiat`, `providers.escrow` | Fixed: `"airtm"` and `"trustless_work"`, regardless of the configured `PAYMENT_PROVIDER` |
| `version` | `npm_package_version` when available, otherwise `"1.0.0"` |

## GET /api/v1/health

The basic check. It does no I/O and answers immediately, so it tells you only that the API process is up. Use it for load balancer and container probes.

## GET /api/v1/health/detailed

The detailed check. It tests the database, Redis, the Airtm API and the Trustless Work API in parallel, each with a 5-second limit, so a slow dependency can make the call take up to about 5 seconds. Use it for monitoring and debugging, not for frequent probes.

### Status semantics

The HTTP status is `200 OK` **even when something is unhealthy**: the handler returns the result instead of throwing. Read `data.status` in the body, not the HTTP code.

| Overall `status` | Rule in `HealthService.check` |
| --- | --- |
| `unhealthy` | At least one dependency is `unhealthy` |
| `degraded` | No dependency is `unhealthy`, and at least one is `degraded` |
| `healthy` | Every dependency is `healthy` |

| Dependency | Can be | Why |
| --- | --- | --- |
| `database` | `healthy`, `unhealthy` | Query succeeds, or fails with the error message |
| `redis` | `healthy`, `unhealthy` | Ping succeeds, or fails with the error message |
| `airtm` | `healthy`, `degraded` | `degraded` with `error: "Not configured"` when `AIRTM_API_KEY` is unset; `degraded` when unreachable or the API answers with a 5xx; otherwise `healthy` |
| `trustlessWork` | `healthy`, `degraded` | Same rules, using `TRUSTLESS_API_KEY` |

So the two provider dependencies can only lower the overall status to `degraded`, never to `unhealthy`. A deployment that has not configured Airtm reports `degraded` permanently.
