OFFER-HUB has two independent credential models. Use the marketplace backend credential for marketplace operations and a signed-in user's JWT for user-facing operations.

| Credential | Where it lives | Lifetime | Resources |
|---|---|---|---|
| API key | Marketplace backend secrets (`ohk_live_…` or `ohk_test_…`) | Long-lived; not sent to business endpoints | API-key administration and minting short-lived tokens |
| API-key token | Marketplace backend or short-lived browser/server handoff (`ohk_tok_…`) | 1 hour | Marketplace backend calls to business endpoints |
| User session JWT | Marketplace frontend/session storage or secure client state | 7 days | Orders, escrow, resolution, disputes, wallet, payouts, bank accounts, and KYC |

<Callout type="warning">
Never embed a marketplace API key in browser code or an end-user application. The API key is exchanged for a one-hour API-key token and the SDK caches and re-mints that token.
</Callout>

## Scopes

API keys use these scopes:

| Scope | Purpose |
|---|---|
| `read` | Read marketplace and user resources |
| `write` | Create or change resources; mint API-key tokens; create users |
| `support` | Manage API keys and inspect the API-key context |

Use the least privilege required. A short-lived `ohk_tok_…` token carries the scopes of the API key that minted it.

## Marketplace API key flow

1. A self-hosted marketplace creates its first API key from the bootstrap master key. Master-key setup belongs only in the self-hosting guide.
2. Store the returned API key in the marketplace backend.
3. Call `POST /api/v1/auth/api-keys/:id/token` with the API key and `write` scope.
4. Use the returned `ohk_tok_…` token for business endpoints.
5. Let the SDK cache the token and re-mint it as needed; tokens expire after one hour.

```http
POST /api/v1/auth/api-keys/:id/token
Authorization: Bearer ohk_live_…
```

The API key and short-lived token are both Bearer credentials, but they have different roles:

- **Never send the API key** to ordinary business endpoints.
- **Send the short-lived token** to business endpoints.
- API-key values are never returned after creation.

## Signed-in user sessions

A user can sign in with a Stellar wallet or email/password. Both paths produce the same 7-day JWT.

### Wallet sign-in

1. Request a challenge from `POST /api/v1/auth/wallet/challenge`.
2. Sign the returned message with the user's Stellar wallet.
3. Verify the signature at `POST /api/v1/auth/wallet/verify`.
4. Use the returned JWT for user-resource endpoints.

### Email/password sign-in

Registration and login are public. Password reset and email verification routes are public unless they explicitly require a JWT, as listed in the endpoint reference.

```http
Authorization: Bearer <7-day user-session JWT>
```

Send the user-session JWT to orders, escrow, resolution, disputes, wallet, payout, bank-account, and KYC resources. API-key scopes do not replace a user's session JWT for these routes.

## Supported Stellar wallets

Users connect a wallet in their browser with Stellar Wallets Kit:

- Freighter (now branded Varial)
- Lobstr
- xBull

The Orchestrator never receives or stores the user's Stellar private key for external wallets.

## API-key endpoint summary

| Method | Path | Auth |
|---|---|---|
| `POST` | `/api/v1/auth/api-keys` | API key, `support` |
| `GET` | `/api/v1/auth/api-keys` | API key, `support` |
| `GET` | `/api/v1/auth/me` | API key context |
| `POST` | `/api/v1/auth/api-keys/:id/token` | API key, `write` |

For request and response fields, see [Auth Endpoints](/docs/api-reference/auth).

## Security guidance

- Store API keys only in marketplace backend secrets.
- Mint and cache API-key tokens in the backend.
- Store user-session JWTs using your application's normal secure session mechanism.
- Revoke a user session from the current session list when a sign-out or account-security action requires it.
- Rotate or replace an API key rather than recovering its plaintext after creation.
