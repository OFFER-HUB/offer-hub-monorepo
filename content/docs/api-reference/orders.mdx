An OFFER-HUB order is the lifecycle root of a marketplace transaction: it records the buyer, the seller, the amount, and the work, and every money movement in the escrow flow is driven by its status. Five endpoints drive an order from creation up to the point where escrow takes over, and two more track delivery against the order's milestones.

| Method | Path | Success status | Controller handler |
| --- | --- | --- | --- |
| <Badge variant="primary">POST</Badge> | `/api/v1/orders` | `201 Created` | `OrdersController.create` |
| <Badge variant="success">GET</Badge> | `/api/v1/orders` | `200 OK` | `OrdersController.findAll` |
| <Badge variant="success">GET</Badge> | `/api/v1/orders/{id}` | `200 OK` | `OrdersController.findOne` |
| <Badge variant="primary">POST</Badge> | `/api/v1/orders/{id}/reserve` | `201 Created` | `OrdersController.reserveFunds` |
| <Badge variant="primary">POST</Badge> | `/api/v1/orders/{id}/cancel` | `201 Created` | `OrdersController.cancel` |
| <Badge variant="success">GET</Badge> | `/api/v1/orders/{id}/milestones` | `200 OK` | `OrdersController.getMilestones` |
| <Badge variant="primary">POST</Badge> | `/api/v1/orders/{id}/milestones/{milestoneRef}/complete` | `201 Created` | `OrdersController.completeMilestone` |

All seven handlers live in `OrdersController` (`apps/api/src/modules/orders/orders.controller.ts`) and delegate to `OrdersService` (`apps/api/src/modules/orders/orders.service.ts`). With the global `/api/v1` prefix set in `apps/api/src/main.ts`, the paths above are the full routes.

<Callout type="note">
  The other four routes on the same controller are documented on their own pages, because they are the money-moving steps: `POST /api/v1/orders/{id}/escrow` and `POST /api/v1/orders/{id}/escrow/fund` in [Escrow Endpoints](/docs/api-reference/escrow), and `release` / `refund` / `dispute` under `/orders/{orderId}/resolution/*` in [Resolution Endpoints](/docs/api-reference/resolution). This page is the lifecycle **up to** funding and the milestone bookkeeping **inside** `IN_PROGRESS`. Field lists here were transcribed from the orchestrator behavior recorded in [Orders SDK Reference](/docs/sdk/orders) (`apps/api/src/modules/orders/dto/create-order.dto.ts`, `apps/api/src/modules/orders/dto/cancel-order.dto.ts`, `packages/sdk/src/resources/orders.ts`), the [Data Model](/docs/guide/data-model) Prisma tables, and the [API Reference overview](/docs/api-reference/overview).
</Callout>

## Common behavior

### Authentication and scope

`OrdersController` declares **no guards and no scopes** — there is no `@UseGuards(ApiKeyGuard, ScopeGuard)` and no `@Scopes(...)` on it (see the same finding for its escrow handlers in [Escrow Endpoints](/docs/api-reference/escrow#authentication-and-scope)). These routes are therefore **not authenticated and not scope-gated in the current Orchestrator**.

| Aspect | Value on these routes | Source |
| --- | --- | --- |
| Authentication | None enforced (no `ApiKeyGuard`) | `apps/api/src/modules/orders/orders.controller.ts` |
| Required scope | None (no `ScopeGuard` / `@Scopes`) | `apps/api/src/modules/orders/orders.controller.ts` |
| Rate limiting | Yes — global `RateLimitGuard` via `APP_GUARD`, 100 requests per 60-second window | `apps/api/src/app.module.ts`, [Rate Limiting](/docs/api-reference/overview#rate-limiting) |
| Correlation | `X-Request-ID` echoed in `meta.requestId` when sent | `CorrelationIdMiddleware`, `ResponseInterceptor` |
| Request body | `create` (required), `cancel` (optional), `complete` (none) | `orders.controller.ts` |

<Callout type="warning">
  The examples below send `Authorization: Bearer …` anyway, because every other reference in these docs does, and because a future release may attach `ApiKeyGuard` to this controller. Today the header is ignored by these seven routes. The scope model that *does* exist (`read`, `write`, `support` — see [API Key Scopes](/docs/api-reference/overview#api-key-scopes)) is enforced on other modules, not here.
</Callout>

### Request validation

The global `ValidationPipe` runs with `whitelist: true`, `forbidNonWhitelisted: true`, and `transform: true` (`apps/api/src/main.ts`), so on the two endpoints that bind a DTO:

- Unknown body properties are **rejected** with `400 VALIDATION_ERROR`, not silently dropped.
- A malformed `amount` (`"100"`, `"100.5"`, `100`, `"$100.00"`) fails the same way — amounts are decimal strings with exactly two places. See [Amounts and currencies](#amounts-and-currencies).

`GET` routes bind no body, and `reserve` / `completeMilestone` bind no DTO either, so the pipe has nothing to reject there.

### Success status codes

None of the four `POST` handlers here (`create`, `reserve`, `cancel`, `completeMilestone`) declares `@HttpCode`, so NestJS applies its default **`201 Created`**; the three `GET` handlers return `200 OK`. That matches the escrow pair ([Escrow Endpoints](/docs/api-reference/escrow#success-status-codes)) and differs from the resolution endpoints, which set `200` explicitly except `dispute`.

### Response envelope

`ResponseInterceptor` (`apps/api/src/common/interceptors/response.interceptor.ts`) wraps the handler's `{ success, data }` payload — `isAlreadyWrapped` only skips wrapping when a `meta` key is present or the payload has exactly one key — so a successful single-resource call looks like this on the wire:

```json
{
  "data": { "success": true, "data": { "...": "order" } },
  "meta": { "requestId": "req_1ab90c", "timestamp": "2026-02-25T12:00:00.404Z" }
}
```

Errors use the single-level envelope from `GlobalExceptionFilter` (`apps/api/src/common/filters/global-exception.filter.ts`): `{ "error": { "code", "message", "details?" } }`.

<Callout type="warning">
  **`details` is not a fixed shape.** For validation failures the error catalog and this page use `details.fields` — an array of `{ field, message }` — while [Resolution Endpoints](/docs/api-reference/resolution#post-apiv1ordersorderidresolutionrefund) shows `details.validationErrors`, a flat array of message strings. Read both, and never assume `details` keys exist: `INSUFFICIENT_FUNDS` carries `{ available, requested }`, `INVALID_STATE` carries the current state, and several codes carry no `details` at all.
</Callout>

<Callout type="tip">
  The TypeScript SDK's HTTP client returns the parsed JSON body typed as the resource, so with this envelope the order actually sits one level deeper. Every SDK example on this page unwraps it the same way the escrow and resolution examples do: `const order = (result as any).data?.data ?? result`.
</Callout>

### Idempotency

<Callout type="danger">
  **None of the seven endpoints on this page honors the `Idempotency-Key` header.** `IdempotencyGuard`, `IdempotencyInterceptor`, and `@IdempotencyTtl()` exist (`apps/api/src/common/guards/idempotency.guard.ts`, `apps/api/src/common/interceptors/idempotency.interceptor.ts`, `apps/api/src/common/decorators/idempotency-ttl.decorator.ts`) but are not attached to `OrdersController`, so a key sent to `/orders*` is ignored — including the `POST /orders` example in [Idempotency](/docs/api-reference/overview#idempotency) and the `sdk.withIdempotencyKey(...)` helper in the [Orders Guide](/docs/guide/orders#2-use-idempotency-keys), which therefore set a header nothing reads here.

  Retries are made safe by the **state machine** instead: `POST /orders` has no replay protection at all (each retry creates a new `ord_` row — deduplicate with the unique `clientOrderRef`), while every state-changing sub-route rejects a replay with `400 INVALID_STATE` once the order has left its required state. See [Known behavior](#known-behavior) for the documents that still claim otherwise.
</Callout>

### Amounts and currencies

| Rule | Detail |
| --- | --- |
| `amount` is a string | Decimal string with exactly two places (`"2500.00"`). Numbers, `"2500"`, `"2500.5"`, and anything with a currency symbol are rejected. |
| `currency` defaults to `"USD"` | Omitting it on create stores `"USD"`; the value is copied onto the escrow row. |
| Settlement is USDC | The escrow leg moves USDC on Stellar regardless of the label, and only USDC is supported for balances today — see [Multi-Currency](/docs/guide/multi-currency). `XLM` and other codes in the [overview](/docs/api-reference/overview) tables are roadmap items. |
| Amount is stored as-is | `order.amount` is the source of truth for `reserve`, escrow creation, and funding; none of those endpoints accept an amount. |

| Endpoint | Order before | Order after |
| --- | --- | --- |
| `POST /orders` | — (new row) | `ORDER_CREATED` |
| `POST /orders/{id}/reserve` | `ORDER_CREATED` | `FUNDS_RESERVED` |
| `POST /orders/{id}/cancel` | `ORDER_CREATED` or `FUNDS_RESERVED` | `CLOSED` (`finalStatus: "CANCELED"`) |
| `POST /orders/{id}/escrow` | `FUNDS_RESERVED` | `ESCROW_CREATING` → `ESCROW_FUNDING` |
| `POST /orders/{id}/escrow/fund` | `ESCROW_FUNDING` | `IN_PROGRESS` (escrow `FUNDED`) |

Transitions are enforced by `OrderStateMachine.assertTransition(from → to)` (`packages/shared/src/utils`), whose table lives with the enum in `packages/shared/src/enums/order-status.enum.ts`. Milestones do **not** advance the order machine: a milestone moves only its own `MilestoneStatus` (`OPEN` → `COMPLETED`), and release is a separate call that requires *every* milestone to be `COMPLETED` — see [Resolution Endpoints](/docs/api-reference/resolution#post-apiv1ordersorderidresolutionrelease).

## POST /api/v1/orders

Creates the order row and, optionally, its milestones. `OrdersService.createOrder` validates the DTO, resolves both parties, checks that the milestone amounts sum to the order amount, and writes the `orders` row in `ORDER_CREATED`. **No funds move and no contract is deployed by this call.**

### Preconditions

1. Both `buyerId` and `sellerId` resolve to existing users — otherwise `404 ORDER_NOT_FOUND`.
2. `buyerId` and `sellerId` differ — sending the same user twice is `400 INVALID_REQUEST`.
3. `amount` matches the decimal-string format — otherwise `400 INVALID_AMOUNT`.
4. When `milestones` are present, their amounts sum **exactly** to `amount`; otherwise the request is rejected before anything is written.
5. `clientOrderRef`, when sent, is not already used by another order (unique column).

### Errors

| HTTP | `error.code` | When |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | A required field is missing, a field has the wrong type or casing, or the body carries an unknown property. `details` lists the field messages. |
| `400` | `INVALID_REQUEST` | `buyerId` and `sellerId` are the same user. |
| `400` | `INVALID_AMOUNT` | `amount` is not a two-decimal string, or the milestone amounts do not sum to it. The error catalog calls the same failure `INVALID_AMOUNT_FORMAT` (`docs/guides/errors-troubleshooting.md`). |
| `404` | `ORDER_NOT_FOUND` | The buyer or seller user ID does not exist — the orders module reports a missing party with the order code, not `USER_NOT_FOUND` (`apps/api/src/modules/orders/exceptions/orders.exceptions.ts`). |

A duplicate `clientOrderRef` violates the unique column (`docs/guides/orders.md`), so treat that reference as your creation idempotency key rather than a retry mechanism.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request body",
    "details": {
      "fields": [
        { "field": "amount", "message": "Must be a string with 2 decimals (e.g., \"50.00\")" },
        { "field": "buyerId", "message": "Required" }
      ]
    }
  }
}
```

## GET /api/v1/orders

Lists orders with cursor pagination and role/status filters. `OrdersService.getOrders` reads the query object, applies the filters, and returns one page plus a cursor.

## POST /api/v1/orders/:id/reserve

Moves `order.amount` from the buyer's **available** balance to **reserved**, so the money cannot be spent on another order while the escrow is being set up. This is the mandatory step before escrow creation.

### Path parameters

<ParamTable
  label="Path parameters"
  fields={[
    { name: "id", type: "string", required: true, description: "Order ID with the ord_ prefix." },
  ]}
/>

<Callout type="tip">
  Send **no body**. The amount is always read from `order.amount` and the currency from `order.currency` — exactly as for the escrow pair, which binds no `@Body()` at all (`orders.controller.ts`, [Escrow Endpoints](/docs/api-reference/escrow#authentication-and-scope)). The `{"amount": "80.00"}` body in the internal walkthrough `docs/guides/orders.md` and the two-argument `sdk.orders.reserve(orderId, { amount })` form in `docs/guides/errors-troubleshooting.md` are not the shape the [SDK reference](/docs/sdk/orders#reserve-funds) documents; do not rely on a body being read.
</Callout>

### Preconditions

1. The order exists — otherwise `404 ORDER_NOT_FOUND`.
2. Order status is `ORDER_CREATED` — otherwise `400 INVALID_STATE` (`InvalidOrderStateException`).
3. The buyer has an active payment account and an available balance covering `order.amount` — otherwise the reservation fails and nothing moves.
4. `OrderStateMachine.assertTransition(ORDER_CREATED → FUNDS_RESERVED)` passes.

### What happens to the money

| Step | Code | Effect |
| --- | --- | --- |
| 1 | `balanceService.reserve(buyer, { amount, currency, orderId, description })` | Buyer `available -= amount`, `reserved += amount`. |
| 2 | `prisma.$transaction` | `order.status = FUNDS_RESERVED`, plus a `FUNDS_RESERVED` audit entry. |
| 3 | `eventBus.emit(ORDER_FUNDS_RESERVED)` | `order.funds_reserved` and `balance.reserved` on the [SSE stream](/docs/api-reference/events). |

## POST /api/v1/orders/:id/milestones/:milestoneRef/complete

Marks one milestone `COMPLETED`. This is a bookkeeping write on the order's milestone row — it moves no money and makes no on-chain call. The on-chain milestone signature happens later, inside `resolution/release`, which refuses to run while any milestone is still `OPEN`.

### Path parameters

<ParamTable
  label="Path parameters"
  fields={[
    { name: "id", type: "string", required: true, description: "Order ID with the ord_ prefix." },
    { name: "milestoneRef", type: "string", required: true, description: "The ref supplied when the order was created, matched against Milestone.milestoneRef. Path segments are read with @Param('milestoneRef'); the overview table shows the same slot as {ref}. Use the milestoneRef value — it is the field name on the resource." },
  ]}
/>

<Callout type="tip">
  This endpoint has **no request body**, and the route binds no DTO — see the [Orders Guide](/docs/guide/orders#complete-a-milestone). Send no `Content-Type: application/json` with an empty object: with `forbidNonWhitelisted: true` an unexpected `{}` is not the risk, but any property you invent is a `400 VALIDATION_ERROR`.
</Callout>

### Preconditions

1. The order exists — otherwise `404 ORDER_NOT_FOUND`.
2. Order status is `IN_PROGRESS` — otherwise `400 INVALID_STATE`. Before funding the order is not in the work window; after release, refund, or dispute it never is again.
3. A milestone with that `milestoneRef` exists **on this order** — otherwise `404 MILESTONE_NOT_FOUND`.
4. The milestone is not already `COMPLETED` — otherwise `400 INVALID_STATE`, which is what makes a retry harmless.

## Events emitted by this group

Every endpoint above publishes domain events to the [SSE stream](/docs/api-reference/events). Filtering is by exact event name, repeated per type (`?types=order.created&types=order.closed&resources=Order`) — `types=order.*` is only valid on the internal event bus, not on the public stream.

| Endpoint | Event | Payload |
| --- | --- | --- |
| `POST /orders` | `order.created` | `{ orderId, buyerId, sellerId, amount, currency, title, description?, clientOrderRef? }` |
| `POST /orders/{id}/reserve` | `order.funds_reserved` | `{ orderId, buyerId, amount, currency, reservedBalance, availableBalance }` |
| `POST /orders/{id}/reserve` | `balance.reserved` | Before/after available and reserved balances for the buyer. |
| `POST /orders/{id}/cancel` | `order.canceled` | `{ orderId, buyerId, canceledBy, reason?, canceledAt, fundsReleased }` |
| `POST /orders/{id}/cancel` | `order.closed` | `{ orderId, finalStatus, closedAt }` |
| `POST /orders/{id}/milestones/{ref}/complete` | `escrow.milestone_completed` | `{ escrowId, orderId, milestoneRef, milestoneTitle, amount, completedAt }` |

<Callout type="warning">
  The milestone event is namespaced under `escrow.*`, not `order.*` — an `order.milestone_completed` event does not exist. Listing only the order event names on your `types` filter will never show milestone completions; add `escrow.milestone_completed` explicitly.
</Callout>

## Error codes for this group

Every code below is defined once in `packages/shared/src/constants/error-codes.ts` and rendered by `GlobalExceptionFilter`.

| Code | HTTP | Endpoints | Meaning |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | `400` | `POST /orders`, `cancel` | DTO validation failed; `details` lists the field messages. |
| `INVALID_REQUEST` | `400` | `POST /orders` | Buyer and seller are the same user. |
| `INVALID_AMOUNT` | `400` | `POST /orders` | Amount format invalid, or milestone amounts do not sum to the order amount. |
| `INVALID_STATE` | `400` | `reserve`, `cancel`, `milestones/{ref}/complete` | The order (or milestone) is not in the state this step requires. |
| `ORDER_NOT_FOUND` | `404` | all seven | Unknown `orderId`, or an unknown buyer/seller ID on create. |
| `MILESTONE_NOT_FOUND` | `404` | `milestones/{ref}/complete` | No milestone with that `milestoneRef` on the order. |
| `INSUFFICIENT_FUNDS` | `422` | `reserve` | Buyer's available balance is below the order amount. |
| `FUNDS_ALREADY_RESERVED` | `409` | `reserve` | The catalog's dedicated code for a second reserve; the state machine often answers `INVALID_STATE` first, so handle both. |
| `RATE_LIMITED` | `429` | all seven | Over the global 100 requests / 60 s window. |
| `INTERNAL_ERROR` | `500` | all seven | Database or provider failure outside the validated flow. |

## Known behavior

<Callout type="danger">
  **Idempotency is documented three ways.** The guards and interceptors are genuinely not attached to `OrdersController` — the same finding the [Escrow](/docs/api-reference/escrow#idempotency) and [Resolution](/docs/api-reference/resolution#idempotency) pages record for the other handlers on those controllers — yet `docs/guides/orders.md` states that "all state-changing order endpoints accept an `Idempotency-Key`", and [Escrow Flows](/docs/guide/escrow-flows) advises always sending one when funding. Plan for the header being ignored: deduplicate creation with `clientOrderRef` and treat `400 INVALID_STATE` as "already done".
</Callout>

<Callout type="warning">
  **`order.dispute` is never populated on read.** `OrdersService.getOrder` includes only `escrow` and `milestones`, so the `dispute` relation on the response is `undefined` even when a dispute exists. Read disputes through `GET /api/v1/disputes/{id}` instead of the order payload — this is also why the "no active dispute" precondition on release and refund never fires from that field ([Resolution Endpoints](/docs/api-reference/resolution#known-behavior)).
</Callout>

<Callout type="warning">
  **`INVALID_STATE` arrives as HTTP `400`, not `422` or `409`.** `InvalidOrderStateException` extends `BadRequestException`, while the shared catalog's `ERROR_HTTP_STATUS` table maps the code to `409` and `docs/guides/orders.md` documents `409 INVALID_STATE` for every rejected transition. Likewise `INSUFFICIENT_FUNDS` is `402` in the SDK reference and `422` in the overview catalog. Trust the status you receive and branch on `error.code`.
</Callout>

<Callout type="note">
  **Cancel and the milestone reference naming.** Cancellation has no `CANCELED` status — the order becomes `CLOSED`, with `finalStatus: "CANCELED"` recorded by the internal walkthrough only. And the path slot for a milestone is written `{ref}` in the [endpoint table](/docs/api-reference/overview#orders) and `{milestoneRef}` in the SDK reference; the field on the resource is `milestoneRef`, so that is the value you substitute.
</Callout>
