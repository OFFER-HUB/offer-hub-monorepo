Read, move, and verify a user's **available** and **reserved** balances. This reference covers all nine routes under `/api/v1/users/:userId/balance`.

<Callout type="note">
  Amounts are decimal strings. Release pays a seller; cancellation returns funds to the same user. Sync compares balances and records discrepancies, but does not adjust the ledger.
</Callout>

## Endpoint directory

| Operation | Method and suffix | Scope | Result in `data` |
| --- | --- | --- | --- |
| [Get](#get) | `GET /balance` | `read` | `Balance` |
| [Verify](#verify) | `GET /balance/verify` | `read` | `Balance` plus `providerVerified` |
| [Credit](#credit) | `POST /balance/credit` | `write` | `BalanceOperationResult` |
| [Debit](#debit) | `POST /balance/debit` | `write` | `BalanceOperationResult` |
| [Reserve](#reserve) | `POST /balance/reserve` | `write` | `BalanceOperationResult` |
| [Release](#release) | `POST /balance/release` | `write` | Seller's `BalanceOperationResult` |
| [Cancel reservation](#cancel-reservation) | `POST /balance/cancel-reservation` | `write` | `BalanceOperationResult` |
| [Deduct reserved](#deduct-reserved) | `POST /balance/deduct-reserved` | `write` | `BalanceOperationResult` |
| [Sync](#sync) | `POST /balance/sync` | `write` | `SyncResult` |

## Request conventions

Every route takes a required `userId` string in the path, conventionally `usr_...`; the controller does not attach an ID-format validation pipe. There are no query parameters or pagination controls. Use an existing user when changing balances.

| Header | Requirement |
| --- | --- |
| `Authorization` | Required: `Bearer $OFFERHUB_API_KEY`; the key needs the endpoint's scope. Keep credentials on your server. |
| `Content-Type` | `application/json` for JSON request bodies. |
| `Idempotency-Key` | Optional UUID v4 on every POST, including sync; recommended for retries. See [Idempotency](#idempotency). |
| `X-Request-ID` | Optional correlation string; generated by the server if absent. Examples use `balance-example`. |

All successful routes return HTTP **200**. The global interceptor wraps the controller result as `{ data, meta: { requestId, timestamp } }`. Errors use `{ error: { code, message, details? } }`. Example IDs, timestamps, and balances below are illustrative fixtures checked against the source, not live account data.

### Body validation

The six amount-changing POST routes inherit these DTO fields. Each endpoint lists its complete body below.

| Field | Type | Required | Constraint / default |
| --- | --- | --- | --- |
| `amount` | string | Yes | Exactly two decimal places, for example `"10.00"`; the service also requires a value greater than zero. JSON numbers and `"0.00"` are not valid operation amounts. |
| `currency` | string | No | Defaults to `"USD"`; no currency enum is enforced by the DTO. It does not convert amounts or change the stored ledger currency. |
| `description` | string | No | Optional audit description; no enum or length bound is declared. |

Credit and debit additionally allow optional `reference: string`. Reserve, release, cancel-reservation, and deduct-reserved require non-empty `orderId: string`; release also requires non-empty `sellerId: string`. These DTOs have **no `reason` field**. Unknown body fields are rejected by the global validation pipe. Optional fields use `IsOptional`, so explicit `null` bypasses their validators; omit unused fields in integrations.

`orderId` is passed as metadata, not looked up to determine an order-specific reserved amount. The service checks the user's aggregate reserved balance. Cancellation affects only the supplied `amount`, not all reservations for that order.

### Response schemas

```typescript
type Balance = {
  user_id: string;
  available: string;
  reserved: string;
  total: string; // available + reserved
  currency: string;
  updated_at: string; // ISO-8601 timestamp
};

type BalanceOperationResult = {
  success: boolean; // true on successful operations
  balance: Balance;
  operation: string; // CREDIT_AVAILABLE, DEBIT_AVAILABLE, RESERVE,
                     // RELEASE, CANCEL_RESERVATION, or DEDUCT_RESERVED
  amount: string;
  previousBalance: { available: string; reserved: string };
  newBalance: { available: string; reserved: string };
  auditLogId: string;
};

type SyncResult = {
  synced: boolean;
  localBalance: string;
  providerBalance: string; // decimal string, or "unknown" on fetch failure
  discrepancy: string; // signed provider minus local available, or "unknown"
  action: "none" | "flagged"; // current implementation never returns "adjusted"
};

type Envelope<T> = {
  data: T;
  meta: { requestId: string; timestamp: string };
};
```

The service's declared `SyncResult` union also includes `"adjusted"`, but no current return branch emits it. Balance mutations return the stored currency, which can differ from a supplied `currency` string.

## Examples setup

Set `OFFERHUB_API_URL` to your deployment's full API prefix, for example `http://localhost:4000/api/v1`, and `OFFERHUB_API_KEY` to your server-side key. Use test users and test funds for these mutation examples. For each POST, generate and persist a fresh UUID v4 as `IDEMPOTENCY_KEY` before the first request; reuse it only for retries of that same operation.

<CommandLine>npm install @offerhub/sdk</CommandLine>

```typescript
import { OfferHubSDK } from '@offerhub/sdk';

const sdk = new OfferHubSDK({
  apiUrl: process.env.OFFERHUB_API_URL!, // includes /api/v1
  apiKey: process.env.OFFERHUB_API_KEY!,
});
// For one POST operation and its retries only:
const operation = sdk.withIdempotencyKey(process.env.IDEMPOTENCY_KEY!);
```

<Callout type="warning">
  At the pinned source revision, SDK request and response declarations lag behind the HTTP API. The SDK HTTP client returns the JSON envelope unchanged. It does not unwrap `data` or translate `reference` into `orderId`, or `recipientId` into `sellerId`. The examples below explicitly bridge these declaration mismatches; they do not modify the SDK or imply runtime validation. Prefer the cURL contract when checking your installed SDK version.
</Callout>

Use the response types above with the TypeScript examples. `as unknown as Envelope<...>` acknowledges the SDK's inaccurate return declaration. For order-related requests, the argument assertion bridges the SDK's old request type while sending only real DTO fields. Do not add `reference` or `recipientId` to satisfy those old declarations: the API rejects those fields on order-related routes.

## Idempotency

GET get/verify do not use idempotency middleware. All seven POST routes support an optional `Idempotency-Key` through the globally registered guard and interceptor. Without it, repeating a mutation can apply it again. `reference` and `orderId` are not deduplication keys.

With a key, the service compares a hash of the request body, replays a stored completed response, and adds `Idempotency-Replay: true`. Changed payloads produce `409 IDEMPOTENCY_KEY_REUSED`; an in-flight request produces `409 IDEMPOTENCY_KEY_IN_PROGRESS`. Malformed UUID v4 keys produce `400 VALIDATION_ERROR`. Use a distinct key for every new operation, even across endpoints and users: the stored identity does not include the URL or HTTP method. The source records a 24-hour expiry, but the lookup does not itself enforce expiry; do not rely on reusing an old key.

The SDK supports `withIdempotencyKey(key)` but does not generate a key automatically. Its HTTP client retries POST requests for selected transient statuses, so supply a stable key before issuing a mutation.

## Common errors

These errors apply to every endpoint unless marked POST-only. Endpoint sections add their domain-specific errors.

| HTTP | Code | Condition |
| --- | --- | --- |
| 401 | `UNAUTHORIZED` | Missing or invalid Bearer credential. |
| 403 | `INSUFFICIENT_SCOPE` | Credential lacks `read` or `write` as required. |
| 429 | `RATE_LIMITED` | Global rate limiter rejects the request. |
| 500 | `INTERNAL_ERROR` | Unhandled database or other server failure; not a documented domain success. |
| 400 | `VALIDATION_ERROR` | POST body fails DTO validation, contains unknown fields, or the supplied idempotency key is malformed. |
| 409 | `IDEMPOTENCY_KEY_REUSED` | POST key reused with a different payload. |
| 409 | `IDEMPOTENCY_KEY_IN_PROGRESS` | POST with that key is still being processed. |

Missing Authorization example (401):

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Missing Authorization header",
    "details": { "requestId": "balance-example" }
  }
}
```

The six amount operations can additionally return `400 INVALID_AMOUNT_FORMAT` after DTO validation (for example `"0.00"`). Their service requires positive amounts. Credit, debit, reserve, cancel-reservation, and deduct-reserved use the atomic helper, which can throw `409 BALANCE_CONCURRENCY_CONFLICT` when a calculated balance would be negative. Release uses its own two-user transaction and does not throw that custom exception. Raw transaction failures can instead reach the global `500 INTERNAL_ERROR` handler.

## Verify

<Endpoint method="GET" path="/api/v1/users/:userId/balance/verify" scope="read" />

A nonzero discrepancy of at most 1.00 returns false; an absolute discrepancy greater than 1.00 throws 409. Not-ready providers or caught balance-fetch failures also return false. ## Release

## Sync

<Endpoint method="POST" path="/api/v1/users/:userId/balance/sync" scope="write" />

Compares provider funds with the local **available** balance and records an audit result. A discrepancy returns `synced: true, action: "flagged"`; no discrepancy returns `synced: true, action: "none"`. Neither branch changes the local balance.

**Source:** [controller](https://github.com/OFFER-HUB/OFFER-HUB/blob/b399e0800298a04caabadf689fed07e25c36abab/apps/api/src/modules/balance/balance.controller.ts); [BalanceService.syncBalanceFromProvider](https://github.com/OFFER-HUB/OFFER-HUB/blob/b399e0800298a04caabadf689fed07e25c36abab/apps/api/src/modules/balance/balance.service.ts).

**Parameters:** required path `userId: string`; no query parameters.

**Body:** none; no DTO is bound to this route.

**Idempotency:** Optional UUID v4 header; use one stable key for this operation and its retries.

<CodeTabs label="Sync request examples" tabs={[
  {
    "label": "cURL",
    "language": "bash",
    "code": "curl --request POST \"$OFFERHUB_API_URL/users/usr_buyer123/balance/sync\" \\\n  --header \"Authorization: Bearer $OFFERHUB_API_KEY\" \\\n  --header \"X-Request-ID: balance-example\" \\\n  --header \"Idempotency-Key: $IDEMPOTENCY_KEY\""
  },
  {
    "label": "TypeScript SDK",
    "language": "typescript",
    "code": "const response = await operation.balance.sync('usr_buyer123') as unknown as Envelope<SyncResult>;\nconsole.log(response.data);"
  }
]} />

**200 response:** `Envelope<SyncResult>` (see [Response schemas](#response-schemas)).

```json
{
  "data": {
    "synced": true,
    "localBalance": "100.00",
    "providerBalance": "100.00",
    "discrepancy": "0.00",
    "action": "none"
  },
  "meta": {
    "requestId": "balance-example",
    "timestamp": "2026-10-22T12:00:00.000Z"
  }
}
```

**Errors:** `404 USER_NOT_FOUND` for an unknown user, plus [Common errors](#common-errors). A failure caught around provider `getBalance` returns 200 with `synced: false`, not a guaranteed 504.

404 example:

```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User not found"
  }
}
```

If the provider is not ready, the response has `synced: false`, all three amount strings `"0.00"`, and `action: "none"` (those zeros do not prove the real ledger is empty). If fetching the provider balance fails after readiness succeeds:

```json
{
  "data": {
    "synced": false,
    "localBalance": "100.00",
    "providerBalance": "unknown",
    "discrepancy": "unknown",
    "action": "none"
  },
  "meta": {
    "requestId": "balance-example",
    "timestamp": "2026-10-22T12:00:00.000Z"
  }
}
```
