This walkthrough takes a running instance to a funded escrow and a released order. It uses `curl` so the request shapes are explicit; the same steps are available through the [SDK](/docs/sdk/quick-start).

<Callout type="tip">
  Complete [Installation](/docs/installation) first and keep a `read`/`write` API key at hand. Examples use `ohk_live_your_api_key` as a placeholder.
</Callout>

## Before you begin

| Requirement | Value |
|---|---|
| Base URL | `http://localhost:4000/api/v1` locally, your HTTPS origin in production |
| Credential | API key with `read` and `write` scopes |
| Network | `testnet` for this walkthrough |
| Money | USDC on the selected Stellar network |

## Step 1 — Create a user

```bash
curl -X POST http://localhost:4000/api/v1/users \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Content-Type: application/json" \
  -d '{
    "externalUserId": "your-buyer-123",
    "email": "buyer@example.com",
    "type": "BUYER"
  }'
```

```json
{
  "data": {
    "id": "usr_...",
    "externalUserId": "your-buyer-123",
    "email": "buyer@example.com",
    "type": "BUYER",
    "status": "ACTIVE"
  }
}
```

IDs are a prefix plus 32 random characters — `usr_`, `ord_`, `esc_`, `dsp_` — not UUIDs. Create a seller the same way with `"type": "SELLER"`.

## Step 2 — Check the balance

```bash
curl http://localhost:4000/api/v1/users/usr_your_user_id/balance \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

```json
{
  "data": {
    "userId": "usr_...",
    "available": "0.00",
    "reserved": "0.00",
    "currency": "USDC"
  }
}
```

A buyer needs `available` funds before checkout. On testnet, fund the buyer from a sandbox wallet or faucet; on mainnet, the buyer deposits USDC from their own wallet.

## Step 3 — Create an order

`POST /orders` requires an `Idempotency-Key`. Derive it from your own order reference so a retry cannot create a second order.

```bash
curl -X POST http://localhost:4000/api/v1/orders \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: your-order-reference-001" \
  -d '{
    "buyerId": "usr_buyer_id",
    "sellerId": "usr_seller_id",
    "amount": "50.00",
    "currency": "USDC",
    "title": "Logo design",
    "description": "Design a logo for a startup"
  }'
```

```json
{
  "data": {
    "id": "ord_...",
    "status": "ORDER_CREATED",
    "buyerId": "usr_...",
    "sellerId": "usr_...",
    "amount": "50.00",
    "currency": "USDC"
  }
}
```

The buyer's `available` balance decreases and `reserved` increases by the order amount.

## Step 4 — Submit the escrow

`POST /orders/:id/escrow/submit` also requires an `Idempotency-Key`. It prepares the Trustless Work escrow and returns the transaction for the buyer's wallet.

```bash
curl -X POST http://localhost:4000/api/v1/orders/ord_your_order_id/escrow/submit \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Idempotency-Key: your-order-reference-001-escrow"
```

The response contains the escrow record and an unsigned transaction. Your frontend passes that transaction to [Stellar Wallets Kit](https://stellarwalletskit.dev); the buyer signs in Freighter/Varial, Lobstr or xBull, and the signed transaction is submitted to Stellar RPC.

<Callout type="warning">
  The Orchestrator never signs for the buyer. If the wallet cancels, no funds move and the order stays in its pre-funding state.
</Callout>

Order status after funding: `ESCROW_CREATING` → `ESCROW_FUNDING` → `ESCROW_FUNDED` → `IN_PROGRESS`.

## Step 5 — Deliver and release

Your marketplace records delivery. Once the order is `DELIVERED`, the buyer requests release:

```bash
curl -X POST http://localhost:4000/api/v1/orders/ord_your_order_id/resolution/release \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Content-Type: application/json" \
  -d '{"requestedBy": "usr_buyer_id"}'
```

The order moves to `RELEASE_REQUESTED`, the buyer signs the release transaction, and the order becomes `RELEASED` then `CLOSED`. The seller's `available` balance is credited.

## Step 6 — Pay out

A seller withdraws to an external Stellar address, or submits a BlindPay payout for a local bank account in Brazil, Mexico, Argentina or Colombia:

```bash
curl -X POST http://localhost:4000/api/v1/orders/ord_your_order_id/payout/submit \
  -H "Authorization: Bearer ohk_live_your_api_key" \
  -H "Idempotency-Key: your-order-reference-001-payout"
```

## The same flow with the SDK

```typescript
import { OfferHubSDK } from "@offerhub/sdk";

const sdk = new OfferHubSDK({
  apiUrl: "http://localhost:4000",
  apiKey: process.env.OFFERHUB_API_KEY!,
});

const buyer = await sdk.users.create({
  externalUserId: "your-buyer-123",
  email: "buyer@example.com",
  type: "BUYER",
});

const seller = await sdk.users.create({
  externalUserId: "your-seller-456",
  email: "seller@example.com",
  type: "SELLER",
});

const order = await sdk.orders.create({
  buyerId: buyer.id,
  sellerId: seller.id,
  amount: "50.00",
  currency: "USDC",
  title: "Logo design",
});

const balance = await sdk.balance.get(buyer.id);
console.log(balance.available, balance.reserved);
```

Escrow submission and release involve wallet signing, so those steps run through your frontend with a short-lived token:

```typescript
// On your server: exchange the API key for a one-hour token for this user.
const scoped = sdk.asUser(userToken);
// On the client: hand the unsigned transaction to Stellar Wallets Kit,
// then submit the signed transaction back to the Orchestrator.
```

## Listen for events

Subscribe to the SSE stream to keep your UI in step:

```bash
curl -N http://localhost:4000/api/v1/events \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

The stream carries order, escrow, balance, dispute and payout events. Treat each event as a notification and re-read the order before acting on money.

## Common errors

| Error code | Cause | Fix |
|---|---|---|
| `INSUFFICIENT_FUNDS` | Buyer's available balance is too low | Fund the buyer before creating the order |
| `INVALID_STATE` | Action not allowed from the current status | Read the order and follow the state machine |
| `USER_NOT_FOUND` | Unknown user ID | Create the user first |
| `IDEMPOTENCY_KEY_REUSED` | Same key, different request body | Use a new key for a new request |
| `INSUFFICIENT_SCOPE` | Key lacks `write` or `support` | Use a key with the right scope |
