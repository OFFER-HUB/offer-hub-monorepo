This tutorial takes you from an empty directory to a working checkout: a buyer and seller, an escrow-protected order, delivery, release and a payout. It uses the testnet sandbox, so no real funds are involved.

<Callout type="tip">
  Every step uses placeholders for credentials and addresses. Keep your `.env` untracked.
</Callout>

## What you will build

```mermaid

    subgraph You["Your marketplace"]

        UI --> API
    end

    WALLET["Buyer wallet<br/>Stellar Wallets Kit"]

    WALLET -->|signs unsigned transaction| RPC[Stellar RPC]
```

You keep the listing, the checkout page and the delivery workflow. The Orchestrator handles balances, escrow, disputes and payouts.

## Part 1 — Run an Orchestrator

### 1.1 Clone and install

```bash
git clone https://github.com/OFFER-HUB/OFFER-HUB.git
cd OFFER-HUB
npm install
```

### 1.2 Start PostgreSQL and Redis

```bash
docker compose up -d
```

### 1.3 Bootstrap with the installer

```bash
npx create-offer-hub-orchestrator
```

Choose `testnet` for the network and enter your testnet Stellar RPC URL. The installer writes `.env`, applies migrations and creates the platform records.

### 1.4 Start the API

```bash
npm run dev
curl http://localhost:4000/api/v1/health
```

### 1.5 Create your API keys

Use the master key once, for the operator key:

```bash
curl -X POST http://localhost:4000/api/v1/auth/api-keys \
  -H "Authorization: Bearer your-master-key" \
  -H "Content-Type: application/json" \
  -d '{"name": "Operator", "scopes": ["support"]}'
```

Then create the backend keys:

```bash
curl -X POST http://localhost:4000/api/v1/auth/api-keys \
  -H "Authorization: Bearer ohk_live_operator_key" \
  -H "Content-Type: application/json" \
  -d '{"name": "Marketplace backend", "scopes": ["read", "write"]}'
```

Store both values. The `key` field is shown once.

## Part 2 — Scaffold your marketplace app

Open a new terminal in another directory.

```bash
mkdir my-marketplace && cd my-marketplace
npm init -y
npm install @offerhub/sdk dotenv
npm install --save-dev typescript tsx @types/node
npx tsc --init --target ES2022 --module NodeNext --moduleResolution NodeNext --outDir dist --strict
```

Create `.env`:

```env
OFFERHUB_API_URL=http://localhost:4000
OFFERHUB_API_KEY=ohk_live_your_api_key
```

Create `src/sdk.ts`:

```typescript
import "dotenv/config";
import { OfferHubSDK } from "@offerhub/sdk";

export const sdk = new OfferHubSDK({
  apiUrl: process.env.OFFERHUB_API_URL!,
  apiKey: process.env.OFFERHUB_API_KEY!,
});
```

<Callout type="danger">
  The SDK is server-side only. Never bundle this file, or the API key, into your frontend.
</Callout>

## Part 3 — Users and sessions

Create the two participants. `externalUserId` is your own identifier, so you can map Orchestrator users back to your accounts.

```typescript
// src/01-users.ts
import { sdk } from "./sdk.js";

async function main() {
  const buyer = await sdk.users.create({
    externalUserId: "marketplace-buyer-001",
    email: "alice@example.com",
    type: "BUYER",
  });

  const seller = await sdk.users.create({
    externalUserId: "marketplace-seller-001",
    email: "bob@example.com",
    type: "SELLER",
  });

  console.log({ buyerId: buyer.id, sellerId: seller.id });
}

main().catch(console.error);
```

```bash
npx tsx src/01-users.ts
```

### Sessions

Your users sign in either with email/password or with a wallet. Both produce the same user JWT, valid for 7 days. Create the session on your backend, then hand the token to your app.

For browser calls, do not ship the API key. Exchange it for a one-hour token on the server and act as the user:

```typescript
const userSdk = sdk.asUser(userToken);
```

## Part 4 — Fund the buyer

Check the balance before checkout:

```typescript
const balance = await sdk.balance.get(buyerId);
console.log(balance.available, balance.reserved);
```

On testnet, fund the buyer's wallet from a sandbox source. On mainnet, the buyer deposits USDC from their own wallet to their own address. The Orchestrator never holds the buyer's key.

## Part 5 — Listing to order

Your marketplace owns listings. When the buyer checks out, create the financial agreement:

```typescript
// src/02-order.ts
import { sdk } from "./sdk.js";

async function checkout(buyerId: string, sellerId: string) {
  const balance = await sdk.balance.get(buyerId);
  if (Number(balance.available) < 75) {
    throw new Error("Buyer needs more funds");
  }

  const order = await sdk
    .withIdempotencyKey("marketplace-order-001")
    .orders.create({
      buyerId,
      sellerId,
      amount: "75.00",
      currency: "USDC",
      title: "Logo design — startup package",
      description: "Three concepts, two revision rounds",
    });

  console.log(order.id, order.status); // ord_..., ORDER_CREATED
  return order;
}
```

The order moves to `FUNDS_RESERVED`: the buyer's `available` balance decreases and `reserved` increases by the order amount.

<Callout type="note">
  Milestones belong to a single order and share its escrow. Pass them at creation if your listing has staged deliverables; they do not create extra orders.
</Callout>

## Part 6 — Escrow with client-side signing

Funding escrow is a three-step exchange:

1. Your backend calls `POST /orders/:id/escrow/submit` with an `Idempotency-Key`.
2. The Orchestrator prepares the Trustless Work escrow and returns an unsigned Stellar transaction.
3. The buyer's wallet signs it. The signed transaction is submitted to Stellar RPC.

```typescript
// Backend: prepare the escrow operation.
const submission = await sdk
  .withIdempotencyKey("marketplace-order-001-escrow")
  .escrow.submit(orderId);

// Send `submission.transaction` to your frontend.
```

```typescript
// Frontend: ask the wallet to sign, then submit.
import { StellarWalletsKit } from "@creit.tech/stellar-wallets-kit";

const signedXdr = await StellarWalletsKit.signTransaction(unsignedXdr, {
  network: "TESTNET",
  address: buyerAddress,
});

await fetch(`${apiUrl}/api/v1/orders/${orderId}/escrow/submit`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${userToken}`,
    "Idempotency-Key": "marketplace-order-001-escrow",
  },
  body: JSON.stringify({ signedTransaction: signedXdr }),
});
```

<Callout type="warning">
  The Orchestrator cannot sign for the buyer. If the wallet rejects or the user cancels, no funds move and the order stays in its pre-funding state.
</Callout>

Status progression:

| Stage | Order status | Funds |
|---|---|---|
| Order created | `ORDER_CREATED` | None reserved |
| Checkout | `FUNDS_RESERVED` | Reserved off-chain |
| Escrow prepared | `ESCROW_CREATING` → `ESCROW_FUNDING` | Reserved |
| Escrow funded | `ESCROW_FUNDED` → `IN_PROGRESS` | In the contract |

## Part 7 — Delivery and release

Delivery is your marketplace's concern. Record it, then let the buyer approve:

```typescript
await sdk.resolution.release(orderId, { requestedBy: buyerId });
```

The order moves to `RELEASE_REQUESTED`, the buyer signs the release transaction from the same wallet, and the order settles as `RELEASED` → `CLOSED`. The seller's `available` balance is credited.

<Callout type="note">
  Confirm the escrow is `ESCROW_FUNDED` and there is no open dispute before release. An event alone is not proof; re-read the order.
</Callout>

## Part 8 — Payout

The seller chooses between an external Stellar address and a local bank account through BlindPay.

```typescript
await sdk
  .withIdempotencyKey("marketplace-order-001-payout")
  .payouts.submit(orderId);
```

| Destination | Preparation |
|---|---|
| External Stellar address | None beyond the address |
| Brazil, Mexico, Argentina, Colombia | Bank account plus the KYC checks for the corridor |

Corridor availability and provider limits come from BlindPay for your account. The Orchestrator adds no fee of its own.

## Part 9 — Disputes

If the work is not delivered or does not match the agreement, either party can open a dispute:

```typescript
const dispute = await sdk.disputes.open(orderId, {
  openedBy: "BUYER",
  reason: "QUALITY_ISSUE",
});
```

| Field | Values |
|---|---|
| Opened by | `BUYER`, `SELLER` |
| Reason | `NOT_DELIVERED`, `QUALITY_ISSUE`, `OTHER` |
| Status | `OPEN` → `UNDER_REVIEW` → `RESOLVED` |

Resolution requires a `support`-scoped key:

```typescript
await sdk.disputes.resolve(dispute.id, {
  decision: "SPLIT",
  releaseAmount: "45.00",
  refundAmount: "30.00",
  note: "Partial delivery accepted by both parties",
});
```

Outcomes are `FULL_RELEASE`, `FULL_REFUND` or `SPLIT`. While a dispute is open, release is frozen.

## Part 10 — Real-time events

Subscribe to the SSE stream so your UI reflects settlement without polling:

```bash
curl -N http://localhost:4000/api/v1/events \
  -H "Authorization: Bearer ohk_live_your_api_key"
```

```typescript
const events = new EventSource(
  "http://localhost:4000/api/v1/events?types=order.escrow_funded,order.released,order.disputed",
  { headers: { Authorization: `Bearer ${apiKey}` } },
);

events.onmessage = (message) => {
  const event = JSON.parse(message.data);
  console.log(event.type, event.data);
};
```

Re-read the order after an event before showing a final state or moving funds in your own system.

## Part 11 — Errors and safe retries

```typescript
import { OfferHubError, InsufficientFundsError } from "@offerhub/sdk";

try {
  await sdk.orders.create(payload);
} catch (error) {
  if (error instanceof InsufficientFundsError) {
    // Prompt the buyer to add funds
  } else if (error instanceof OfferHubError) {
    console.error(error.code, error.message);
  } else {
    throw error;
  }
}
```

Three operations require an idempotency key: order creation, escrow submission and payout submission. Retry them with the same key and the same body; a new key is a new operation.

See [Errors](/docs/sdk/errors) for the full code list.
