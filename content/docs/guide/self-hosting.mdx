Running the Orchestrator yourself gives you control over data, uptime and configuration. This guide covers infrastructure, environment, bootstrap, upgrades and operations.

<Callout type="tip">
  Configure the variables on the [Configuration](/docs/configuration) page before you start. Every value in this guide is a placeholder.
</Callout>

## What you are running

A self-hosted deployment has four moving parts:

```mermaid
flowchart LR
    API["Orchestrator API<br/>REST + SSE + jobs"]
    PG[(PostgreSQL)]
    RD[(Redis)]
    RPC[Stellar RPC]
    TW[Trustless Work]
    BP[BlindPay]

    API --> PG
    API --> RD
    API --> RPC
    API --> TW
    API --> BP
```

- **API** — serves the REST API, the SSE event stream and the background job workers.
- **PostgreSQL** — users, balances, orders, escrows, disputes and audit records.
- **Redis** — job queues, idempotency records and rate limiting.
- **External providers** — Stellar RPC, Trustless Work for escrow, BlindPay for off-ramp.

You do not run a second worker process. The API process consumes the queues.

## Prerequisites

- Docker 20.10+ and Docker Compose 2.0+
- PostgreSQL 14+ (local or managed)
- Redis 6+ (local or managed, with TLS in production)
- A domain name and TLS certificate for the API origin
- At least 1 GB RAM and 10 GB disk for the API host, plus your database's requirements

```bash
docker --version && docker compose version
```

## Infrastructure with Docker Compose

Create a deployment directory and a Compose file for the dependencies:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: offerhub
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: offerhub
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U offerhub"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres_data:
  redis_data:
```

```env
POSTGRES_PASSWORD=your-database-password
```

<Callout type="warning">
  This Compose file provides PostgreSQL and Redis only. The API is built and run from the application repository, or deployed with a build-based platform configuration.
</Callout>

Managed services work too. Point `DATABASE_URL` and `REDIS_URL` at them and drop the corresponding Compose service.

## Build and run the API

Clone the starter shell and build it:

```bash
git clone https://github.com/OFFER-HUB/OFFER-HUB.git
cd OFFER-HUB
npm ci
npm run build
```

Run the API with the environment from your secret store:

<CommandLine>npm start</CommandLine>

### Environment

```env
NODE_ENV=production
PORT=4000
PUBLIC_BASE_URL=https://api.yourdomain.example

DATABASE_URL=postgresql://user:password@host:5432/database?sslmode=require
REDIS_URL=rediss://host:6379

OFFERHUB_MASTER_KEY=your-master-key

TRUSTLESS_API_KEY=your-trustless-api-key
TRUSTLESS_WEBHOOK_SECRET=your-trustless-webhook-secret

STELLAR_NETWORK=mainnet
STELLAR_RPC_URL=https://your-stellar-rpc-endpoint
STELLAR_USDC_ASSET_CODE=USDC
STELLAR_USDC_ISSUER=your-usdc-issuer
```

<Callout type="danger">
  Never commit this file. Rotate `OFFERHUB_MASTER_KEY` out of runtime use once the operator and backend keys exist.
</Callout>

## Bootstrap an instance

A fresh instance has no API keys. Bootstrap in this order:

1. **Set the master key.** Put `OFFERHUB_MASTER_KEY=your-master-key` in the environment.
2. **Apply migrations.**
   ```bash
   npx prisma migrate deploy
   ```
3. **Create the operator key** with `support` scope:
   ```bash
   curl -X POST https://api.yourdomain.example/api/v1/auth/api-keys \
     -H "Authorization: Bearer your-master-key" \
     -H "Content-Type: application/json" \
     -d '{"name": "Operator", "scopes": ["support"]}'
   ```
4. **Create the marketplace keys** with `read` and `write` scopes, using the operator key.
5. **Store the keys** in your marketplace backend's secret store. Remove the master key from the running service if your deployment allows it.

<Callout type="note">
  The master key is a bootstrap credential, not a daily-use one. Give it the shortest possible life in your runtime environment.
</Callout>

## Network and signing

| Concern | Production | Sandbox |
|---|---|---|
| Network | `STELLAR_NETWORK=mainnet` | `STELLAR_NETWORK=testnet` |
| RPC | A mainnet Stellar RPC endpoint | A testnet Stellar RPC endpoint |
| Signing | User wallet via Stellar Wallets Kit | User wallet, or the sandbox's invisible wallets |
| User keys | Never held by the Orchestrator | Sandbox wallets exist for demos |

In production the Orchestrator returns unsigned transactions. The user's wallet (Freighter/Varial, Lobstr or xBull) signs and submits them. If your deployment logs request bodies, make sure signed transaction payloads are not captured in full.

## TLS

Terminate TLS at your load balancer or reverse proxy. Minimum requirements:

- HTTPS only; redirect HTTP.
- `PUBLIC_BASE_URL` matches the public origin exactly, so provider callbacks reach the instance.
- WebSocket upgrades are not required; the SSE stream is plain HTTPS.

Example Nginx location:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:4000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off; # keep the SSE stream flowing
}
```

`proxy_buffering off` matters for `GET /api/v1/events`; buffering delays events until the buffer fills.

## Health and monitoring

```bash
curl https://api.yourdomain.example/api/v1/health
```

```json
{
  "status": "healthy",
  "services": {
    "database": "connected",
    "redis": "connected"
  }
}
```

Operational checks worth alerting on:

- Health endpoint non-200 for more than two minutes.
- Queue depth growing without draining.
- Stellar RPC error rate rising.
- Provider webhook failures in the dead-letter queue.

## Upgrades

1. Back up the database.
2. Pull the new source revision.
3. Install dependencies and build.
4. Apply migrations.
5. Restart the API.
6. Verify health and one read-only API call.

```bash
# 1. Backup
pg_dump "$DATABASE_URL" > backup-$(date +%Y%m%d).sql
# 2. Update source
git pull --ff-only
# 3. Build
npm ci && npm run build
# 4. Migrate
npx prisma migrate deploy
# 5. Restart your service manager, then:
curl -fsS https://api.yourdomain.example/api/v1/health
```

If a release misbehaves, check out the previous known-good commit, rebuild and restart. Migrations are not automatically reversible; restore the backup if a migration must be undone.

## Background jobs

The API process runs BullMQ queues for provider webhooks, reconciliation and notifications. See [Background Jobs](/docs/guide/background-jobs) for queue names, retry behaviour and how to inspect them.

## Security checklist

- [ ] `NODE_ENV=production`
- [ ] Master key removed from runtime use after bootstrap
- [ ] `read` and `write` keys separated from the `support` key
- [ ] Database and Redis reachable only from the private network
- [ ] `DATABASE_URL` and `REDIS_URL` use TLS
- [ ] `TRUSTLESS_WEBHOOK_SECRET` configured
- [ ] HTTPS enforced for `PUBLIC_BASE_URL`
- [ ] Logs exclude secrets and full signed transaction payloads
- [ ] Backups scheduled and restore tested
