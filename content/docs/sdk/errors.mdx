Every Orchestrator error uses the same envelope, whatever the endpoint:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Available balance is less than the requested amount",
    "details": {
      "available": "25.00",
      "requested": "75.00"
    }
  }
}
```

`details` is optional and its shape depends on `code`. Treat `code` as the stable contract; `message` is for humans and may change.

Successful responses use the matching success envelope:

```json
{ "data": { "...": "..." }, "meta": { "...": "..." } }
```

`meta` is optional and carries pagination or request context.

## Codes

| Code | HTTP | Meaning | What to do |
|---|---|---|---|
| `VALIDATION_ERROR` | 400 | A field is missing or invalid | Fix the request body |
| `UNAUTHORIZED` | 401 | Credential missing, malformed or expired | Send a valid key or token |
| `INSUFFICIENT_SCOPE` | 403 | Credential lacks the route's scope | Use a key with `read`, `write` or `support` as needed |
| `USER_NOT_FOUND` | 404 | Unknown user ID | Create the user first |
| `ORDER_NOT_FOUND` | 404 | Unknown order ID | Check the ID, then list orders |
| `INVALID_STATE` | 409 | Transition not allowed from the current status | Read the resource and follow the state machine |
| `IDEMPOTENCY_KEY_REUSED` | 409 | Same key sent with a different body | Use a new key for a new request |
| `INSUFFICIENT_FUNDS` | 422 | Available balance is too low | Fund the account before retrying |
| `RATE_LIMITED` | 429 | Too many requests | Back off, then retry with the same idempotency key |
| `PROVIDER_TIMEOUT` | 504 | Stellar or a provider did not answer in time | Retry with the same idempotency key |

## Typed errors in the SDK

The SDK maps responses to error classes, so you can branch on type instead of parsing strings:

```typescript
import {
  InsufficientFundsError,
  NotFoundError,
  ValidationError,
  InvalidTransitionError,
  OfferHubError,
} from "@offerhub/sdk";

try {
  await sdk.orders.create(payload);
} catch (error) {
  if (error instanceof InsufficientFundsError) {
    // Show a "add funds" state to the buyer
  } else if (error instanceof ValidationError) {
    console.error(error.details);
  } else if (error instanceof NotFoundError) {
    console.error("Unknown resource");
  } else if (error instanceof InvalidTransitionError) {
    // Re-read the resource before retrying
  } else if (error instanceof OfferHubError) {
    console.error(error.code, error.message);
  } else {
    throw error;
  }
}
```

## Retrying safely

Only three operations require an `Idempotency-Key`:

| Operation | Field |
|---|---|
| Create an order | `POST /orders` |
| Submit an escrow transaction | `POST /orders/:id/escrow/submit` |
| Submit a payout | `POST /orders/:orderId/payout/submit` |

Retry those with the **same** key and the same body. A new key is a new operation and can move funds twice.

<Callout type="warning">
  For any other request, read the current state before retrying. A blind retry on a non-idempotent route can duplicate work.
</Callout>

## What not to log

Error `details` can contain amounts or identifiers. Never log credentials, signed transactions, bank details or KYC data. Redact before sending an error to an external logger.

Every failure raised by `@offerhub/sdk` extends the base `OfferHubError`. Catching a specific subclass lets you branch on business failures (`InsufficientFundsError`) versus infrastructure failures (`ProviderError`) versus developer mistakes (`ValidationError`).

## Base class: `OfferHubError`

| Member | Type | Description |
|---|---|---|
| `message` | `string` | Human-readable description returned by the API. |
| `code` | `string` | Machine code from the Orchestrator catalog (`VALIDATION_ERROR`, `INSUFFICIENT_FUNDS`, …). |
| `statusCode` | `number` | HTTP status of the response, or `0` for network-level failures. |
| `response` | `unknown` | Raw response body. |

```typescript
import { OfferHubError } from "@offerhub/sdk";

try {
  await sdk.orders.get("ord_missing");
} catch (error) {
  if (error instanceof OfferHubError) {
    console.error(error.code, error.statusCode, error.message);
  }
}
```

## Error catalog

Named SDK subclasses map to the Orchestrator HTTP statuses and server codes below. When a response has no dedicated subclass, handle it through the base `OfferHubError`. Codes come from `docs/api/errors.md` in the Orchestrator repo; the status mapping matches the JSON error envelope documented in `docs/ai-context.md`.

| SDK class | HTTP | Server codes | When it fires | Retry? |
|---|---|---|---|---|
| `AuthenticationError` | `401` | `UNAUTHORIZED` | Missing or invalid API key. | No |
| `AuthorizationError` | `403` | `INSUFFICIENT_SCOPE` | Valid key, but lacks the required scope for this route. | No |
| `NotFoundError` | `404` | `USER_NOT_FOUND`, `ORDER_NOT_FOUND`, `ESCROW_NOT_FOUND`, `DISPUTE_NOT_FOUND`, `MILESTONE_NOT_FOUND` | The resource ID does not exist. | No |
| `ValidationError` | `400` | `VALIDATION_ERROR`, `INVALID_REQUEST` | Payload failed DTO validation or an order uses the same buyer and seller. | No |
| `InsufficientFundsError` | `422` | `INSUFFICIENT_FUNDS` | Balance cannot cover the reserve or debit. | No |
| `OfferHubError` | `422` | `INVALID_AMOUNT` | Split dispute resolution amounts are missing or do not total the order amount. | No |
| `InvalidTransitionError` | `409` | `INVALID_STATE` | State machine rejects the requested transition. | No |
| `OfferHubError` | `409` | `BALANCE_CONCURRENCY_CONFLICT`, `BALANCE_DISCREPANCY` | Balance changed concurrently or differs from the provider; refresh or reconcile before proceeding. | No |
| `IdempotencyError` | `409` | `IDEMPOTENCY_KEY_REUSED` | Same `Idempotency-Key` replayed with a different body. | No |
| `ProviderError` | `502` / `504` | `PROVIDER_ERROR`, `PROVIDER_TIMEOUT` | Upstream provider (Stellar, AirTM, Trustless Work) failed. | Yes |
| `RateLimitError` | `429` | `RATE_LIMIT_EXCEEDED` | API key exceeded its bucket. | Yes |
| `NetworkError` | — | — | No HTTP response was received (DNS, TCP, TLS, timeout). | Yes |

<Callout type="note">
  `NetworkError` has no HTTP status because the request never reached the Orchestrator. Check `error.cause` for the underlying socket error.
</Callout>

## Class-specific properties

Most classes add nothing beyond the base. Two add useful context.

### `ValidationError`

```typescript
if (error instanceof ValidationError) {
  for (const fieldError of error.errors) {
    console.error(fieldError.field, fieldError.message);
  }
}
```

| Member | Type | Description |
|---|---|---|
| `errors` | `Array<{ field: string; message: string }>` | Field-level validation failures. |

### `InsufficientFundsError`

```typescript
if (error instanceof InsufficientFundsError) {
  console.error(`Need ${error.required}, have ${error.available}`);
}
```

| Member | Type | Description |
|---|---|---|
| `required` | `string` | Amount needed for the operation, e.g. `"100.00"`. |
| `available` | `string` | Available balance at the time of the attempt. |

## Handling pattern

Branch from most specific to least specific, and end with the base class as a catch-all:

```typescript
import {
  OfferHubSDK,
  OfferHubError,
  ValidationError,
  NotFoundError,
  InsufficientFundsError,
  InvalidTransitionError,
  IdempotencyError,
  ProviderError,
  RateLimitError,
  NetworkError,
} from "@offerhub/sdk";

const sdk = new OfferHubSDK({
  apiKey: process.env.OFFERHUB_API_KEY!,
});

try {
  await sdk.orders.reserve("ord_123");
} catch (error) {
  if (error instanceof InsufficientFundsError) {
    return { ok: false, reason: "TOPUP_REQUIRED" };
  }
  if (error instanceof NotFoundError) {
    return { ok: false, reason: "ORDER_MISSING" };
  }
  if (error instanceof InvalidTransitionError) {
    return { ok: false, reason: "WRONG_STATE" };
  }
  if (error instanceof ValidationError) {
    return { ok: false, reason: "INVALID_INPUT", fields: error.errors };
  }
  if (error instanceof IdempotencyError) {
    throw error;
  }
  if (error instanceof RateLimitError || error instanceof ProviderError || error instanceof NetworkError) {
    return { ok: false, reason: "TRANSIENT" };
  }
  if (error instanceof OfferHubError) {
    return { ok: false, reason: error.code };
  }
  throw error;
}
```

## Retry semantics

Automatic retries are handled inside the SDK and governed by `retryAttempts` (default `3`) on `OfferHubSDKConfig`. Retryable classes use exponential backoff; the exact schedule is an implementation detail but never exceeds `timeout` per attempt.

| Class | Auto-retried | Why |
|---|---|---|
| `NetworkError` | Yes | The connection may succeed next time. |
| `ProviderError` | Yes | Upstream provider is the flaky layer. |
| `RateLimitError` | Yes | Backoff eventually clears the bucket. |
| `AuthenticationError` | No | Wrong key, retrying cannot help. |
| `AuthorizationError` | No | Wrong scope, retrying cannot help. |
| `NotFoundError` | No | Resource does not exist. |
| `ValidationError` | No | Payload is wrong. |
| `InsufficientFundsError` | No | Business state. |
| `InvalidTransitionError` | No | State machine rejected it. |
| `IdempotencyError` | No | Developer mistake. |

To disable retries entirely for a specific call, construct a client with `retryAttempts: 0`:

```typescript
const strict = new OfferHubSDK({
  apiKey: process.env.OFFERHUB_API_KEY!,
  retryAttempts: 0,
});

await strict.orders.reserve("ord_123");
```

## Error envelope

Every SDK exception is a projection of the Orchestrator's JSON error envelope:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Available balance 40.00 is less than required 100.00",
    "details": { "required": "100.00", "available": "40.00" }
  }
}
```

The SDK lifts `code`, `message`, and `details` onto the thrown instance and classifies the exception by matching the HTTP status and code against the table above. See `docs/api/errors.md` in the Orchestrator repo for the full server-side catalog.
