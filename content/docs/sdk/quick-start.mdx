`@offerhub/sdk` is the TypeScript client for the Orchestrator API. It handles authentication, retries, idempotency and typed errors.

<Callout type="note">
  This page targets **`@offerhub/sdk` 3.0.0**. Earlier releases had a different resource surface — no `topups` resource, and escrow, resolution and payouts are first-class.
</Callout>

## Installation

```bash
npm install @offerhub/sdk
```

## Configuration

```typescript
import { OfferHubSDK } from "@offerhub/sdk";

const sdk = new OfferHubSDK({
  apiUrl: process.env.OFFERHUB_API_URL!, // e.g. https://your-orchestrator.example.com
  apiKey: process.env.OFFERHUB_API_KEY!, // e.g. ohk_live_...
});
```

### Two credential kinds

| Credential | Prefix | Lifetime | Use it for |
|---|---|---|---|
| API key | `ohk_live_...` | Until revoked | Server-to-server calls from your marketplace backend |
| Scoped token | `ohk_tok_...` | 1 hour | Browser or per-user work, after exchanging an API key |

```typescript
// Server-side integration: the API key stays on the server.
const sdk = new OfferHubSDK({
  apiUrl: process.env.OFFERHUB_API_URL!,
  apiKey: process.env.OFFERHUB_API_KEY!,
});

// Acting as a signed-in marketplace user with a one-hour token.
const userSdk = sdk.asUser(userToken);
```

<Callout type="danger">
  An API key must never reach a browser bundle. Exchange it for a short-lived token on your server, or create the user session there, and use `sdk.asUser(token)` for user-scoped work.
</Callout>

## Resources

| Resource | Purpose |
|---|---|
| `sdk.auth` | Credential exchange and session handling |
| `sdk.users` | Create and read marketplace users |
| `sdk.balance` | Available and reserved balances |
| `sdk.orders` | Order lifecycle |
| `sdk.escrow` | Trustless Work escrow operations and transaction submission |
| `sdk.resolution` | Release, refund and resolution requests |
| `sdk.disputes` | Open, review and resolve disputes |
| `sdk.wallet` | Wallet details and deposits |
| `sdk.withdrawals` | Withdrawals to an external Stellar address |
| `sdk.payouts` | BlindPay off-ramp payouts |
| `sdk.bankAccounts` | Payout bank accounts |
| `sdk.kyc` | Payout onboarding checks |

## Creating a user

```typescript
const buyer = await sdk.users.create({
  externalUserId: "your-buyer-123",
  email: "buyer@example.com",
  type: "BUYER", // BUYER | SELLER | BOTH
});

console.log(buyer.id); // usr_ + 32 random characters
```

`externalUserId` maps the Orchestrator user to your own user record. Keep it stable and unique.

## Creating an order

`orders.create` requires an idempotency key. Set one per logical order so retries are safe:

```typescript
const sdkForOrder = sdk.withIdempotencyKey("your-order-reference-001");

const order = await sdkForOrder.orders.create({
  buyerId: buyer.id,
  sellerId: seller.id,
  amount: "75.00",
  currency: "USDC",
  title: "Logo design",
  description: "Three concepts, two revision rounds",
});

console.log(order.status); // ORDER_CREATED
```

## Escrow and signing

Escrow operations produce **unsigned Stellar transactions**. Your frontend hands them to Stellar Wallets Kit; the user signs; the signed transaction is submitted. The SDK never signs on behalf of a user.

```typescript
const submission = await sdk.escrow.submit(order.id, {
  idempotencyKey: "your-order-reference-001-escrow",
});

// submission.transaction is an unsigned transaction for the buyer's wallet.
// Sign it with Freighter/Varial, Lobstr or xBull, then submit the signed result.
```

Escrow states follow the order lifecycle: `ESCROW_CREATING`, `ESCROW_FUNDING`, `ESCROW_FUNDED`, then `IN_PROGRESS`.

## Release, refund and payouts

```typescript
// Buyer requests release after delivery
await sdk.resolution.release(order.id, {
  requestedBy: buyer.id,
});

// A seller's payout: Stellar address, or a BlindPay corridor
await sdk.payouts.submit(order.id, {
  idempotencyKey: "your-order-reference-001-payout",
});
```

BlindPay covers four corridors: Brazil, Mexico, Argentina and Colombia. Bank account and KYC resources prepare the payout destination.

## Disputes

```typescript
await sdk.disputes.open(order.id, {
  openedBy: "BUYER", // BUYER | SELLER
  reason: "QUALITY_ISSUE", // NOT_DELIVERED | QUALITY_ISSUE | OTHER
});

// Resolution needs the `support` scope
await sdk.disputes.resolve(disputeId, {
  decision: "SPLIT", // FULL_RELEASE | FULL_REFUND | SPLIT
  releaseAmount: "45.00",
  refundAmount: "30.00",
  note: "Partial delivery accepted by both parties",
});
```

Dispute statuses are `OPEN`, `UNDER_REVIEW` and `RESOLVED`.

## Idempotency

Three endpoints require an `Idempotency-Key`:

| Operation | SDK call |
|---|---|
| Create order | `sdk.orders.create` |
| Submit escrow | `sdk.escrow.submit` |
| Submit payout | `sdk.payouts.submit` |

Retrying with the same key returns the original response. Retrying with a new key is a new operation.

<Callout type="warning">
  Never regenerate the key when retrying a failed request. Derive it from your own order reference.
</Callout>

## Error handling

Errors follow the API envelope and are exposed as typed errors by the SDK:

```typescript
import { OfferHubError, ValidationError } from "@offerhub/sdk";

try {
  await sdk.orders.create(payload);
} catch (error) {
  if (error instanceof ValidationError) {
    console.error("Invalid request", error.details);
  } else if (error instanceof OfferHubError) {
    console.error(error.code, error.message);
  }
}
```

The full envelope and error code list is in [SDK Errors](/docs/sdk/errors).
